     Graphing feature: select columns → interactive chart window

     Context

     The dataset table already supports selecting multiple columns (header-click
     selection + the _ColumnToggleFilter toggle-deselect behavior added
     earlier this session). The user wants to turn that selection into an
     actual chart: pick 2+ columns, choose which one is the X-axis and what
     chart type each other column should render as, and get a genuinely
     interactive, modern-looking graph — not a static image. Matplotlib/seaborn
     were explicitly ruled out (their interaction model — click-drag rectangle
     zoom, no built-in cross-series hover — was called out as "clunky"). The
     target feel is closer to a polished web dashboard: smooth zoom/pan, and
     hovering the chart shows every visible series' value at that x in one
     tooltip.

     Decided architecture: embed Plotly.js inside a QWebEngineView, styled
     to match the app's own light/dark palette, with no new Python plotting
     dependency (plotly.min.js is vendored as a static asset; the JSON spec is
     built by hand from Python's json module). This was chosen over
     matplotlib (rejected for interactivity) and over pyqtgraph (native and
     lightweight, but reaching Plotly's out-of-the-box polish would take
     significant manual styling work) after discussing the tradeoff explicitly
     — the real cost is that QWebEngineView bundles Chromium, which is a
     heavier, less "pure-Qt-native" dependency than the rest of this app and
     will matter for eventual installer size.

     Confirmed risk, not yet resolved: a spike run during planning shows
     QWebEngineView currently fails to import in this dev sandbox
     (ImportError: libnspr4.so: cannot open shared object file), needing
     libnspr4, libnss3, libnssutil3, libsmime3, libasound2t64,
     libxkbfile1 — all available via apt-get in this sandbox, and the user
     account has sudo group membership so a plain sudo apt-get install may
     just work (untried). This must be resolved before the GraphWindow
     piece can be tested end-to-end here; everything else in this plan (data
     fetching, numeric detection, Plotly spec generation, the config dialog) is
     plain Python/Qt-widget code with no such dependency and is fully
     testable regardless.

     Decided design points (from discussion)

     - Chart types: Line, Scatter, Bar, Histogram.
     - Large datasets: cap + warn. New MAX_PLOT_ROWS = 20_000 constant;
       if a column has more rows than that, plot the first MAX_PLOT_ROWS and
       show a truncation warning, reusing the exact same amber warn-color
       convention already used for the "showing first N of M flattened
       columns" warning (#E0A93B dark / #8A5A00 light).
     - Only numeric columns are plottable. Non-numeric columns in the
       current selection are excluded from the config dialog. If fewer than 2
       numeric columns remain selected, clicking "Make Graph" shows a
       status-bar error instead of opening the dialog.
     - Histogram vs. Line/Scatter/Bar: a two-axis-group layout. All
       Line/Scatter/Bar series share one set of axes (rows sorted ascending by
       the chosen X column so lines render correctly), with
       hovermode: 'x unified' giving one tooltip listing every series' y at
       the hovered x. Any Histogram-typed series get their own separate
       subplot stacked below, overlaid together (barmode: 'overlay',
       partial opacity). If every selected series is Histogram, skip the
       primary axes and render just the histogram subplot.
     - Series colors reuse palette.column_color(index) — the same 6-color
       cycle already tinting table columns — so a series' plot color visually
       matches its column's tint in the table.
     - Window chrome: neither the config dialog nor the graph window use
       the app's frameless custom title-bar style. Both follow the existing
       FileOpenDialog precedent — normal OS window decorations, themed only
       via stylesheet/theme.register.
     - Modality: the config dialog is a real modal (QDialog.exec()); the
       graph window is a plain non-modal top-level QWidget shown via
       .show(), so the user can keep browsing the table with it open, and can
       open more than one.
     - Toolbar: keep Plotly's own built-in modebar (pan/zoom/reset/
       download-png), CSS-restyled to match the palette, rather than building
       custom controls — no need to reinvent what Plotly already does well.
     - Theme live-updates: if the user toggles light/dark while a graph
       window is open, push new colors via Plotly.relayout(...) through
       QWebEnginePage.runJavaScript() rather than reloading the page.

  1. The crash you hit: App installed its edge-resize-cursor event filter
     QApplication-wide (needed since the frameless window has zero margin, so
     mouse events land on child widgets first). That means it observed every
     event in the whole process — including QWebEngineView's internal
     GPU/renderer-process objects, which it was never meant to touch. I
     confirmed this precisely: even a completely empty, do-nothing global filter
     reproduces the identical crash the moment any QWebEngineView exists. Fixed
     by scoping the filter to only App's own widget tree (self +
     self.findChildren(QWidget)) instead of the whole application — it still
     catches resize-hover everywhere in the window, but never sees anything
     belonging to the separate graph window.
  2. A related root cause: Qt WebEngine requires
     QApplication.setAttribute(Qt.ApplicationAttribute.AA_ShareOpenGLContexts)
     to be set before the QApplication is constructed. This app never set it,
     which lines up with the GPU-command-buffer errors I kept seeing during
     testing. Added it in main().

     table's column tint colors (deliberately near-invisible against the
     background, e.g. #20262E on a #242424 background). Added a separate, vivid

     tracking the cursor continuously — with sparse data this reads as the line
     jumping/lagging behind smooth mouse movement. Set spikesnap: 'cursor'
     explicitly so it tracks the pointer directly.
